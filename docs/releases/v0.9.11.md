# adOmnia 0.9.11 - performance flows that explain the load

This release makes Flow Stress useful for repeatable performance engineering,
not just a burst of concurrent requests. AI-authored and manually-authored flows
use the same runtime, including response data handoffs, retries and recovery
branches. Plans, datasets, history and reports remain local.

## Workload modelling

- Load, Spike and Soak are editable staged workloads with a target user count,
  duration, ramp and measurement toggle for every phase.
- Warm-up and cooldown traffic is visible but excluded from percentiles, APDEX
  and release gates, so setup and cache priming do not skew comparisons.
- The local Flow Stress ceiling increases from 25 to 200 virtual users. Actual
  active users are recorded over time instead of assuming the configured target
  was reached.
- CSV headers become flow variables per iteration. Rows can be allocated
  sequentially, per VU or pseudo-randomly; built-in iteration, VU, timestamp and
  UUID variables make unique payloads possible without scripts.

## Results that support a decision

- The result view adds an active-VU timeline, latency distribution histogram,
  APDEX score and a persisted 12-run p95/RPS regression trend.
- Traffic and error rate retain independent axes. Per-step p50/p95/p99 bars,
  baseline markers and SLO lines remain legible in narrow or resized panels.
- Offline HTML reports carry the same workload, latency and distribution charts.
  CSV rows identify phase and whether a sample participated in release metrics.
- APDEX joins p95, error rate and throughput as an optional release gate.
- Recent summary history is stored locally per flow and can be selected directly
  as a comparison baseline.

## Headless flow stress in CI

- **CI plan** exports a portable `*.stress.json` containing the flow graph and
  workload configuration, without runtime samples or dataset contents.
- `adomnia stress <plan>` runs that graph without opening the desktop UI. It
  preserves variable substitution, response-body extraction, success/error
  branches, retries, scripts, assertions, cookies and staged workloads.
- `--dataset`, repeated `--env-var`, CLI/JSON/JUnit reporters and `--out` make the
  same plan reproducible in CI. Request failures or failed release gates return
  exit code 1; invalid configuration returns exit code 2.

## Scope and compatibility

- Existing Flow JSON and stress-result JSON stay compatible. Older baselines
  receive safe defaults for APDEX, distributions, measured duration and active
  users when opened.
- This remains a local load generator. Multi-machine worker coordination is not
  presented as available; use the portable headless plan on controlled runners
  when load must originate from dedicated hosts.
