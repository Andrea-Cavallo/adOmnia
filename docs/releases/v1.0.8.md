# adOmnia 1.0.8 — Workspace più veloci e Code Studio più reattivo

19 ottobre 2026.

## Workspace API

- **Caricamento "tree-first".** I metadata dell'albero (nomi, metodi, url, note) sono separati dal contenuto delle richieste: passare a un workspace inattivo mostra la struttura prima di analizzare corpi e header. Il prefetch parte a riposo o passando il mouse sull'elenco dei workspace, quindi il passaggio di solito legge dalla cache.
- **Idratazione delle richieste sotto controllo.** Salvataggio, export e condivisione attendono sempre i contenuti completi: un'anteprima parziale non viene mai salvata né esportata, e un workspace con contenuti in attesa non viene serializzato, così uno shard completo non può mai essere sovrascritto con meno dati.
- **Migrazione compatibile degli shard.** Gli shard scritti dalle versioni precedenti restano leggibili e ricevono la proiezione dell'albero al salvataggio successivo; i corpi delle richieste restano nel payload completo, quindi le versioni precedenti li leggono senza migrazioni. `collections/all` resta uno snapshot completo versione 2 per il downgrade e viene ricostruito fuori dalla transazione di salvataggio (con flush all'arresto).

## Code Studio

- **Rilevamento progetti con una sola scansione del disco.** Le unità Go, Java e web nascono dalla stessa visita alle cartelle, ognuna con i propri limiti di profondità e di unità; un detector in errore non nasconde gli altri.
- **Layout di sessione salvati per sessione.** Ogni layout (tab aperti, file attivo, split, segnalibri, breakpoint) vive sotto la propria chiave: salvare i tab non riscrive più tutte le altre sessioni. Lo snapshot di stato continua a rispecchiarli per il downgrade.
- **Progetti recenti più leggeri.** L'esistenza delle cartelle è verificata al più una volta per percorso ogni 15 secondi, con cache limitata; le variazioni di disponibilità non riscrivono più lo stato.
- **Misure di caricamento.** `GetWorkspaceLoadPerformance()` riporta restore, rilevamento progetto, avvio watcher e pronto del language server (conteggio, ultimo, massimo); il registratore di avvio misura ogni cambio sessione, non solo il primo ripristino. Le misure restano locali e non toccano il flusso degli eventi di sessione.

## Correzioni

- **gopls carica solo i moduli dei file aperti.** Da 1.0.6 ogni unità era una cartella di workspace: in un progetto con molti moduli gopls creava una vista per modulo e le caricava tutte all'avvio. Ora riceve la sola radice e trova da solo il modulo di ogni file aperto (verificato su sei moduli annidati: 2 viste invece di 6).
- **I language server restano attivi a riposo** e gli avvii lenti sono registrati con le fasi; un server che esce durante la terminazione forzata non registra più un falso errore.
- **Race sui watcher alla chiusura.** Un avvio di watcher in gara con la chiusura del progetto poteva lasciare attivo un watcher per una sessione chiusa (visibile su Linux in CI): l'avvio ora ricontrolla la sessione prima di registrarsi.

## Verifiche

Suite Go completa (inclusa la suite completa di Code Studio, ~700 s), 2083 test frontend, TypeScript, build e budget di startup (640.484 / 650.000 byte, nessun modulo differito nel grafo iniziale) passati. I test del watcher e dei cicli di sessione passano 20 esecuzioni consecutive.

L'accettazione nativa delle ottimizzazioni (avvio a freddo/caldo, primo passaggio a un workspace inattivo, ripristino e cambio ripetuto di sessioni con più tab e split, buffer recuperati, cambiamenti su disco) e il confronto dei tempi nativi sullo stesso dataset restano aperti in [WORKSPACE-LOADING-OPTIMIZATION.md](https://github.com/Andrea-Cavallo/adOmnia/blob/v1.0.8/docs/WORKSPACE-LOADING-OPTIMIZATION.md) e nelle voci manuali di `mds/MANUAL-CHECK.md`. Nessuna percentuale di accelerazione è dichiarata senza il confronto nativo: la documentazione elenca cosa è stato ottimizzato, non quanto.
