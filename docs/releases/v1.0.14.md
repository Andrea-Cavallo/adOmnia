# v1.0.14 — secret masking for AI providers, agent boundaries and startup evidence

This release hardens what leaves the machine when an AI feature is active, and
documents the limit of the filters that adOmnia can actually enforce. No project
data format changes and no migration is required.

## AI and privacy

- **Copilot buffers are redacted before synchronization.** Every opened or
  changed document passes through a shared Go redactor (`internal/airedact`)
  before the Copilot language server sees it, including unsaved buffers. It masks
  private keys, JWTs, GitHub/Stripe/Slack/Google/AWS tokens, passwords in
  connection strings and values assigned to `password`, `secret`, `token`,
  `apiKey` and similar names. The mask preserves byte length, UTF-16 width and
  line breaks, so completion positions remain valid. Chat messages receive the
  same backend defence even though the renderer already redacts them.
- **Agent boundaries are documented, not implied.** `.adomnia/aiignore` filters
  the context adOmnia prepares for Copilot, milk, Claude Code and OpenCode. It is
  not an OS sandbox: the ACP agents run their own tools and can read any file
  their process can open, and ACP exposes no per-file read restriction for
  adOmnia to impose. The Code Studio guide now says this explicitly and the agent
  chat shows a notice when the project has an aiignore. `.adomnia/ai-policy.json`
  remains the hard boundary: `off` blocks every agent and `local-only` restricts
  them to local models.
- **Tests for every entry point.** `internal/copilot`, `internal/milk`,
  `internal/claudecode` and `internal/opencode` cover prompt/document redaction,
  the project policy and the disabled-start path.

## Build and documentation

- **Wails version guard.** `scripts/check-wails-version.mjs` compares `go.mod`
  with `docs/BUILD.md`, `README.md`, `AGENTS.md` and every workflow. The build
  workflow runs it on each change, so the CLI and the module cannot drift again.
- **Vault page.** `docs/VAULT.md` collects age+scrypt, the identity held only in
  memory, auto-lock (30 minutes by default, configurable 1–120), the automatic
  AES-256-GCM seal for database DSNs/passwords through the OS keychain or DPAPI,
  the fallback key file, recovery and an explicit threat model.
- **Startup evidence.** `docs/PERFORMANCE.md` documents the measurement method
  and the first native Windows result; the raw samples are in
  `docs/performance/startup-2026-10-22-windows.json`. The README does not publish
  native startup figures while macOS and Linux are still unmeasured.

## Performance

- Native Windows, empty Hub, 3 launches with an isolated profile: **987 ms**
  median from launch to the first stable frame, **175.4 MB** median peak
  process-tree working set up to that frame, and about **42 ms** in the backend
  `OnStartup` stages. macOS and Linux require real machines and remain pending.

## Verification

`go build ./...`, `go vet` on the changed packages, the focused Go suites
(`internal/airedact`, `internal/copilot`, `internal/milk`, `internal/claudecode`,
`internal/opencode`), `npx tsc --noEmit`, `npm run build` and
`node scripts/check-wails-version.mjs` pass. The complete frontend and Go suites
were not rerun for this release. Native macOS/Linux startup and the Windows
WebView2 startup are not covered by an automated test.

**Not included:** the concurrent integration work on program services and Java
spring data sources is not part of this release.
