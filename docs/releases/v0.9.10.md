# adOmnia 0.9.10 - AI-assisted flows and trustworthy diagnostics

This release turns raw local evidence into a reproducible investigation and
turns a plain-language API scenario into an executable flow. It also makes
stress results useful as a release decision instead of only a table of numbers.
Files, indexes, generated flows and investigation evidence remain local.

## AI Flow Architect

- Describe calls in natural language: for example, call A, extract a field from
  its JSON response, insert it into B as `{{customerId}}`, and call D when B
  times out, has no response or returns an HTTP error such as 500.
- The AI contract now distinguishes successful and failed response branches,
  validates one entry node and executable branch topology, and rejects duplicate
  outgoing branches or invalid extraction variables.
- The preview makes the proposed execution understandable before it changes the
  canvas: it lists data handoffs, fallback paths, variables and warnings, then
  applies a readable automatic layout.
- Generated flows use the existing local runner. Response extraction, template
  interpolation, retries, assertions and branch execution therefore behave the
  same in AI-created and manually-created flows.

## Stress tests that explain the result

- Start with Smoke, Load, Spike or Soak presets and tune users, ramp-up,
  iterations/duration and think time.
- Set release gates for maximum p95 latency, maximum error percentage and
  optional minimum requests per second. Every completed run produces a clear
  pass, fail or insufficient-evidence verdict with the exact checks behind it.
- Overall p95/p99, transfer rate, aggregate status totals and per-step
  percentiles expose both user impact and the responsible step.
- Deterministic diagnostics identify thin samples, long latency tails,
  concentrated errors, the primary bottleneck and regressions against a loaded
  baseline. Each finding includes a concrete next action.
- Error messages are normalized into fingerprints so repeated failures with
  different IDs or numbers are grouped instead of flooding the report.
- CSV, JSON and offline HTML evidence remains exportable. HTML reports include
  the verdict, checks, diagnosis and grouped errors; older v1 JSON baselines are
  normalized when loaded.

## Log Inspector P3

The Log Inspector now supports the complete four-service acceptance journey
captured in the original release-notes work log:

- Import any extension and detect JSON objects, arrays, JSON Lines, Go
  `slog`/`zap`, plain text and mixed prefixed logs from their content. Escaped
  JSON payloads are decoded and Java/Go stack traces remain attached to their
  originating event.
- Save reusable parsing profiles for timestamp, level, message, service and
  correlation fields. Preview profile matches before applying them to a source.
- Search a correlation/request/trace ID and retain exact source file and line
  provenance across calls, request/response bodies, retries and the final
  outcome.
- Surface integrity evidence rather than hiding ambiguity: missing timestamps
  or IDs, clock skew, truncated input, incomplete responses and uncertain
  correlations are explicit findings.
- Compare a failed request chain with a successful one and highlight the body,
  header, query and status differences that explain the divergence.
- Extract latency/error metrics and apply deterministic diagnostic rules without
  sending logs away from the machine.
- Use the local investigation assistant to summarize only the loaded evidence,
  cite event/source references, identify uncertainty and suggest next checks.
- Open an observed application frame, prepare an editable Composer request and
  save, close, reopen and export redacted evidence with bookmarks and notes.
- Keyboard search, Escape handling and resizable investigation panels are
  covered by the final scenario contract on Windows, Linux and macOS CI.

## Reliability and maintenance

- Right-click variable actions now work in wrapped and non-JSON body editors.
- Wails and the Go/frontend dependency set were refreshed together.
- The Wails development root is resolved consistently when the dev task starts
  from the repository root.

## Compatibility

- Existing flow and workspace data remains compatible.
- Stress JSON stays at schema version 1; absent enhanced fields in old exports
  are reconstructed on import.
- Log Inspector sessions retain their existing versioned local format.
