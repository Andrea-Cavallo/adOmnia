# Workspace loading optimization

Implementation checkpoint: 2026-10-19. No native timing measurements yet.

## API workspace

- [x] A1: bootstrap first uses a read transaction. A valid legacy snapshot requests a write transaction only when migration needs to persist shards. The entire bootstrap is re-read in that transaction to preserve a consistent snapshot. A regression test verifies that subsequent bootstraps do not advance the database transaction ID.
- [x] A2: validate workspace JSON in the workspace decoder, check the already validated collections value's array type without decoding every collection again, encode index metadata separately and append the raw collection bytes. The V2 bootstrap trusts this validated active payload instead of calling `json.Valid` again.
- [x] A3: tree metadata (ids, names, methods, urls, notes) is stored separately from request contents. Each workspace shard keeps a `tree` projection next to the complete `collections` payload; the migration is compatible in both directions: shards without a projection keep loading and receive one on their next save, and the complete `collections` bytes still carry every request body so older builds read them unchanged. The renderer hydrates request contents from the structured payload after the tree renders, and the save, export and share paths hydrate first so a preview stub is never persisted or exported (`workspaceSplit.ts`, `collections.ts`, `WorkspacePanel`, `CollectionTree`, `collectionSync`).
- [x] A4: the complete v2 downgrade snapshot `collections/all` is no longer rebuilt inside the save transaction. `Save` schedules a coalesced deferred rebuild (250 ms) that re-encodes every workspace outside the hot path, `FlushLegacySnapshot` rebuilds it synchronously for tests and application shutdown, and a rebuild queued by one database can never write into a later one. The snapshot stays complete and never contains the tree projection.
- [x] A5: idle and hover prefetch of inactive workspace shards (`workspacePrefetch.ts`, bounded to four entries and invalidated on save) and a structured workspace IPC response: `LoadCollectionWorkspaceV2` returns the metadata plus tree projection and the request contents as JSON text, so the renderer parses the tree first and hydrates contents afterwards. The workspace switcher prefetches on hover; startup prefetches the remaining workspaces on idle.

## Code Studio

- [x] B1: restored sessions start watching on their first `GetSessionView`, rather than all projects being scanned at restore. New projects retain their existing watcher startup. Directory scans and gitignore loading run outside the manager lock; Stop cancels an in-progress walk and Shutdown prevents late registrations.
- [x] B3, parallel restoration: directory, runs, view/recovery and Run configuration loading overlap. Saved tabs load concurrently, retaining their saved order and explicit session ID even if the user switches projects during restoration. A failed view restore can be retried.
- [ ] B3, active tab only: deferred. Current document tabs require loaded editor documents; placeholders and split-view restoration need a separate implementation.
- [x] B2: shared project detection walk. `project.WalkDirectories` visits each directory once and shares every visit (and its file list) with all language visitors; Go, Java and web detection collect units from the same walk, keeping their own depth and unit limits, and a visitor that stops descending only stops its own subtree. Partial results and per-language errors survive a failed detector.
- [x] B4: per-session persistence and bounded recent-project filesystem checks. Session layouts are written under their own `session-view:<id>` key, so saving tabs or breakpoints never rewrites every session; the state snapshot keeps mirroring them and remains the source for stores without per-session keys. Recent-project availability is re-checked at most once per path every 15 seconds, the cache is bounded to the recent-project size, and availability changes never trigger a state rewrite (it is derived data).
- [x] B5, initial frontend instrumentation: first-session request, first directory response and restored tabs use the existing local startup recorder. `getStartupDurations()` exposes `studioFirstTreeMs` and `studioTabsRestoredMs`. Marks describe the first session only; the tree mark measures receipt of data, not a rendered frame.
- [x] B5, remaining instrumentation: backend restore, detect-units, watcher-ready and language-server readiness (process start to ready, every start including restarts) use `GetWorkspaceLoadPerformance()` with per-stage count, latest and max. Measurements stay out of the session event stream and remain local. Repeated session switches are measured in the startup recorder: `getStudioSwitchDurations()` keeps a bounded sample list and `getStartupDurations()` publishes numeric summaries (`studioSwitchCount`, `studioSwitchLastMs`, `studioSwitchMaxMs`).

## Compatibility and acceptance
