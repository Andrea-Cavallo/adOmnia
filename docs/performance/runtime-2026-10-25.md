# Runtime memory and CLI cold start — 2026-10-25

Measured on the release build (`wails3 task build`, `-tags production`, 113.8 MB) on the same host as
[stress-2026-10-24](stress-2026-10-24.md): Windows 11 Pro 26300, i7-14700KF (28 logical CPUs), 63.8 GB.
Process tree from `Win32_Process` (parent → child, recursive), working set (WS) and private bytes per
process. Two fixes were measured before and after on the same machine, the same day.

## 1. Restored background projects started Eclipse JDT LS

State restored at launch: three Code Studio sessions — `adOmnia` (active, Go) and two Java projects
that were open in the list but not visible (`threadlocks-example`, `pluginsystem`).

| Build | Processes | Whole tree WS | Whole tree private | JDT LS |
| --- | ---: | ---: | ---: | --- |
| Before (exe of 18:56) — 60 s, 5 samples | 14 | **2,084 MiB** | 2,703 MiB | 2 instances, 830 MiB WS / 1,552 MiB private, started at +7 s |
| After (fix) — 60 s, 5 samples | 10 | **1,115 MiB** | 1,054 MiB | none |
| After, ~2 min, a JSON file open in the active project | 13 | 1,079–1,327 MiB | 1,012–1,184 MiB | none (`vscode-json-language-server` 80 MiB, started by the open file) |

Breakdown before the fix (last sample): JDT LS 830 · gopls 630 · WebView2 renderer 177, browser 123,
GPU 88, utilities 75 · `adomnia.exe` 126 · 4 `conhost` 37 MiB.

Cause: `watchServerDocuments` (`frontend/src/stores/ideLanguageServers.ts`) pre-started JDT LS for
every session with Java units, so each Java project in the list cost a JDT LS at every launch. Now the
pre-start applies to the active session only (`autoStartSessions`) and runs again when the user
selects another session; opening a Java file still starts the server.

## 2. `adomnia mcp` waited for the desktop app's database lock

25 fresh spawns, time to the first `initialize` reply (`startup-bench.mjs`, same client as 2026-10-24):

| Build | Desktop app | min | p50 | p95 | max | failures |
| --- | --- | ---: | ---: | ---: | ---: | ---: |
| Before | open | 272 ms | **278 ms** | 406 ms | 471 ms | 0 |
| After | closed | 36 ms | **42 ms** | 195 ms | 195 ms | 0 |
| After | open | 36 ms | **39 ms** | 188 ms | 220 ms | 0 |

The p95 after the fix comes from one or two spawns out of 25 (OS scheduling); min and p50 are stable.

`GODEBUG=inittrace=1` showed `init main` at 243 ms. Two package-level costs ran before the CLI
dispatch:

- `startupWindowChrome` opened `adomnia.db` read-only with a 250 ms lock timeout: while the desktop
  app held the database, every CLI spawn waited the whole timeout. It is now read in `main()` after
  the dispatch.
- `ensureHiddenConsole` called `AllocConsole` (50–190 ms and one extra `conhost.exe`) for processes
  launched without a console, CLI included. The CLI talks over pipes and launches no console tools, so
  it now skips it; the desktop app keeps it.

## 3. Shutdown

`CloseMainWindow` with the project open: the app exits in 0.3–1 s and **0 of 13–14 child processes
survive** (gopls, JDT LS, JSON language server, WebView2, conhost).

Open observation: a second launch sent while the first instance was still shutting down left both
processes alive without a window for over 60 s (the first one had already lost its children). Not
reproduced on a clean close; tracked as PERF-5.M2.
