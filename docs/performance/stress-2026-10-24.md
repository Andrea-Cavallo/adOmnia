### Memory during a sustained run

The stress process (CLI) sampled every second:

| Run | Requests | Start | Peak |
| --- | --- | --- | --- |
| 20 VU × 10 s | 9,503 | 28.3 MB | 314.8 MB |
| 20 VU × 30 s | 27,360 | 32.4 MB | 349.8 MB |
| 20 VU × 60 s | 56,564 | 36.5 MB | 348.1 MB |

Six times the requests, the same peak: memory plateaus around 315–350 MB after the first seconds
instead of growing per request. There is no per-request leak, but the steady state is high for a load
generator.

### Failure reporting

A plan pointing at a closed port reports the reason instead of a bare `ERR`:

```json
"errors": 20,
"statuses": { "ERR": 20 },
"errorGroups": [ { "message": "Get \"http://127.0.0.1:19999/nothing\": dial tcp 127.0.0.1:19999: connectex: … actively refused it.", "count": 20, "steps": ["GET dead:19999"] } ],
"gateFailures": [ "error rate 100.0% exceeds 1.0%" ]
```

Groups are keyed by a fingerprint (`<id>` for UUIDs, `<n>` for numbers ≥ 3 digits, at most 200 groups) so
ids and ports do not create one group per request, while the message shown is the real one.

Failures count as *frustrated* in APDEX, so an unreachable target reports **APDEX 0.000** rather than
`1.000`. Percentiles skip only requests that never received an HTTP response (a refused connection has
no server latency; its few milliseconds are the connect attempt), so a slow `5xx` or a failed assertion
still shows up in p95/p99, and a p95 gate with nothing measured fails instead of passing with `p95 0 ms`.

The same rules run in the desktop Flow Builder (`createStressAccumulator`), which previously counted
failed samples as satisfied.

### Plans from the Flow Builder

A plan exported from the UI uses every node kind it can create, including the `extract` node that comes
from a recorded script step, plus per-request `extractions` and `condition` nodes. The CLI runner decodes
and executes all of them:

| Node | Behaviour |
| --- | --- |
| `start` | entry point |
| `request` | sends the request, applies its `extractions` to the variables on success |
| `extract` | applies its `extractions` and continues on `next` |
| `condition` | evaluates `source`/`path`/`operator`/`value` and follows `true`/`false` |
| `end` | ends the iteration |

A plan that cannot run is rejected with a reason instead of reporting zero requests: node without
id/type, duplicate node id, unknown node type, edge to a missing node, or a graph with no reachable
request (`flow executed no request`).

| State | `adomnia.exe` | WebView2 (6 processes) | Language servers | Whole tree |
| --- | --- | --- | --- | --- |
| Three sessions restored, idle 2 min | CPU 0.03 %, WS 151 MB | ~467 MB | gopls 95 + 127 MB, JDT LS 527 + 353 MB, rust-analyzer 27 MB | 1807.6 MB / 19 processes |
| Restart with adOmnia open, idle 90 s | CPU **0.017 %**, WS 111 MB | ~440 MB | gopls 128 MB, JDT LS 519 + 358 MB | 1587.2 MB / 14 processes |

The whole-tree figure is dominated by the Java language servers; the adOmnia process itself stays at
111–151 MB.

Shutdown (`CloseMainWindow`, 25 s window): the app exits and **0 of 13 child processes survive**.
The six `msedgewebview2` processes still alive on this machine belong to `SearchHost.exe`, not to
adOmnia — checked to avoid a false orphan report.

## 5. How to reproduce

```bash
# build the same artifact
wails3 task build

# CLI: startup of the MCP endpoint, cold, 25 times
node startup-bench.mjs "C:\path\to\adomnia.exe" mcp 25

# workspace load of a real language server
node gopls-bench.mjs "%APPDATA%\adomnia\goide\tools\bin\gopls.exe" "C:\path\to\project" 3

# load: any plan exported from Flow Builder (Flow Builder → export .stress.json)
adomnia.exe stress checkout.stress.json --reporter json
adomnia.exe stress checkout.stress.json

# the same through MCP
adomnia.exe mcp        # then tools/call stress_run { "plan": "checkout.stress.json" }
```
